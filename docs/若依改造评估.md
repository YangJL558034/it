# 若依 Vue 3 改造评估（2026-10-16）

## 结论与范围

推荐方案 A：保留 ASP.NET Core 10 业务后台及 PostgreSQL，只将 PC 管理应用接入官方若依 Vue 3 前端。此文是改造前评估；当前 1.0.2 尚未集成若依框架，不把已有自研布局称作若依。本次先交付工位交互修正和 SOP 结构整理，不推倒重写。

## 实际工程核查

- `web`：Vue 3、TypeScript、Element Plus、Vite，工位/TV 共用 Capacitor Android 工程；TV 使用 Apache ECharts。
- `server/Mes.Api`：ASP.NET Core 10、EF Core、Npgsql/PostgreSQL、SignalR。生产过站、仪器接收、SOP、报表、备份是实际数据库与文件服务。
- `installer`：Inno Setup 和 .NET 安装辅助程序；离线 PostgreSQL 组件、自包含 Windows 服务、数据库初始化/升级。
- `dist`：旧原型，含浏览器模拟数据和本地文件存储，只作视觉与交互参考。
- 已有迁移：`20261015104008_InitialSchema`、`20261015112614_ConfigurableRolePermissions`、`20261015112748_TestSopSnapshot`、`20261016010310_RememberStation`。前三个属于已有版本，第四个为本次工位持续登录新增。
- 已实现接口分区：`/api/auth/*`、`/api/admin/*`、`/api/catalog`、`/api/station/*`、`/api/trace`、`/api/instrument/v1/*`、`/api/sop/*`、`/api/messages*`、`/api/reports/*`、`/api/tv`、备份/恢复及配置接口。具体路由以 `docs/服务端API.md`、仪器协议文档及源码为准。

## 两种方案

| 项目 | A：若依 Vue 3 前端 + 现有 .NET（推荐） | B：若依 Java + Vue 3 |
|---|---|---|
| PC 基础管理 | 接入若依布局、路由、菜单、标签页、权限指令；适配用户角色、登录、审计、配置 | 使用若依 Java 基础模块，重新对接 MES |
| MES 服务 | 保留 Production、Instruments、Sop、Reporting、Operations；按业务模块迁移前端 | 重写业务服务、事务、幂等、仪器适配、文件、后台任务、恢复控制 |
| 数据 | 保留全部 UUID、外键、密码哈希、工单批次、测试历史、附件路径；新增菜单权限表使用 EF 迁移 | MyBatis/SQL 适配 PostgreSQL，或另行制定到 MySQL 的数据转换；需处理 UUID、时间、JSON、密码哈希格式、约束与审计 |
| 工位与 TV | 保留现有界面、APK、SignalR、原 API；PC 适配层独立 | 必须维持旧 API 和 SignalR 兼容，或同步升级终端，不能直接切换协议 |
| 正式安装 | 自包含 .NET + PostgreSQL + 静态前端；无需 Node/Java/开发工具 | 打包 JRE、数据库；标准若依还使用 Redis。重新设计 Windows 服务、离线安装、升级和恢复 |
| 升级回退 | 新前端可分阶段启用；数据库仅增量迁移；升级前完整备份 | 需要经过演练的数据迁移与双向核验，无法仅替换 EXE 回退 |
| 主要成本 | 接口契约、权限粒度、业务页面重组与回归 | 上述成本加整套业务重写和历史数据迁移；当前没有收益足以抵消风险 |

官方部署文档的 Java 版本随 Spring Boot 分支而不同；若选择 B 必须先固定分支与 JRE 版本，不混用。保留 PostgreSQL 不等于原版若依 Java 可以直接无改动运行。

## A 的落地边界与工程组织（拟议，尚未创建）

```text
admin-web/                  若依 Vue 3 PC 应用，锁定上游提交并保留 MIT 许可
  src/api/mes/              对现有 MES API 的类型化适配
  src/views/mes/            工单批次、追溯、仪器、SOP、报表等专用业务页
  src/views/system/         用户、角色、菜单、参数和日志
web/                        保留工位和 TV 的界面、交互、APK 工程
server/Mes.Api/AdminShell/   PC 菜单/权限契约，业务仍调用原服务
server/Mes.Api/{Production,Instruments,Sop,Reporting,Operations}/
installer/                  构建并打包两个前端，服务端统一托管
```

1. 固定官方若依前端版本/提交，优先评估官方 TypeScript 版本；保留开源许可，检查依赖漏洞。不能覆盖现有 PDF 修复版本和 TV 图表依赖。
2. 若依默认 `/login`、`/getInfo`、`/getRouters`、`/logout` 与当前 `/api/auth/*` 不同。由 PC API 适配层转换账号字段、用户/角色/权限结构与错误格式；保持当前服务器会话验证，不伪造 JWT。
3. 菜单可见性由服务端有效权限生成；按钮权限与服务端授权策略一致。目前 `Office/Quality/Operate/Manage/Board/ReadProduction` 等现有策略需逐项盘点后细分，不能把“菜单隐藏”视为服务端授权。
4. 若新增可编辑菜单/按钮权限关系，必须新增 EF 迁移并给已有角色做明确映射；不删旧表、不重置用户、不导入若依演示密码。若依基础页面也需要真实 .NET API 适配，不能宣称引入前端即拥有 Java 全部功能。
5. MES 页以真实操作流程编排：SOP 库与版本审核发布、设备协议与接收异常、条码追溯、批次筛选导出。代码生成只能辅助主数据表单，不能替代五工序校验。
6. PC 可先在独立路径试运行，旧后台保留回退入口；工位 `/station`、TV `/tv` 与现有 API 不变。切换前验证直接 URL 刷新、权限越权、文件下载、实时更新和安装器静态文件路由。

## 不可回退的业务验收底线

单入口自动扫码；服务器防跳站与跨批次拦截；FAIL 不放行；重复绑定/上传幂等；所有复测与参数保留；厂家协议独立适配（缺文档不得启用）；按工序多文件 SOP 与过站版本快照；批次强制筛选导出；真实数据库及附件备份恢复；Windows 离线安装/升级/恢复；旧终端 API 兼容。全部在隔离测试环境验收后再发布正式升级包。
